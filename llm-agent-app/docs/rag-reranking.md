# RAG: фильтрация, реранкинг и query rewrite (день 23)

Документ описывает второй этап RAG по заданию преподавателя: фильтр релевантности по
порогу cosine (после поиска), настраиваемые топ-K до и после фильтрации, query rewrite
LLM перед ретривалом и сравнение режимов «без фильтра / с фильтром / фильтр + rewrite».
Поведение описано строго по коду (см. раздел 9 «Исходники»); детальная схема API зафиксирована
в `CONTRACT.md`, секция «База знаний / RAG (день 22/23)».

## 1. Цель (задание)

Задание: «Добавить второй этап после поиска: reranker или фильтр релевантности. Настроить
порог отсечения нерелевантных результатов и топ-K до/после фильтрации. Добавить query
rewrite. Сравнить качество без фильтра и с фильтром. Настройки вынести на фронт в меню».

Выбранный вариант второго этапа — **фильтр по порогу similarity** (в задании «reranker ИЛИ
фильтр»): детерминирован, бесплатен, не требует отдельной модели-реранкера (её доступность
в GPUStack не гарантирована). Существующая сортировка чанков по cosine уже выполняет
реранкинг по релевантности; новый этап — управляемая воронка с порогом отсечения.
Отдельный LLM-реранкер (cross-encoder / LLM-скоринг чанков) сознательно вне скоупа.

Результат: **улучшенный RAG = фильтрация/реранкинг + query rewrite + сравнение режимов.**

## 2. Механика воронки

Один запрос агента (текст последнего user-сообщения, либо его переписанная версия,
раздел 4) проходит цепочку в `KbRagService.buildContextResult`:

```
все чанки активных проиндексированных баз (candidateChunks)
  -> cosine-оценка каждого чанка (scored)
  -> сортировка по score DESC
  -> top candidateK                 (candidates)
  -> [если filterEnabled] score >= minScore   (passedFilter)
  -> top topK                       (уходит в промпт)
  -> сборка блока "### База знаний" до MAX_BLOCK_CHARS = 6000 (usedChunks)
```

- Ровно 1 вызов эмбеддинга на запрос (модель — дефолтная каталога, сейчас
  `qwen3-vl-embedding-8b`); чанки всех активных проиндексированных баз загружаются одним
  запросом к БД, cosine считается в Kotlin.
- **Порог** (`minScore`, диапазон 0..1): чанки с `score < minScore` отбрасываются. Если
  после порога не осталось ни одного чанка (`passedFilter = 0`) либо ни один чанк не влез
  в лимит блока, блок `### База знаний` НЕ собирается, и агент отвечает без базы знаний
  (fail-open: run не роняется). Это и есть «отсечение нерелевантных результатов».
- **Блок**: записи вида `[КБ <имя базы> | <файл>#<секция>]` + текст чанка, суммарно не
  более 6000 символов; запись, которая не влезла, просто не добавляется (обрезки середины
  нет).
- Нет активных проиндексированных баз -> поиск не запускается вовсе (нулевых сетевых
  вызовов). Любой сбой (эмбеддинги, БД, сборка) -> warn в серверный лог + блок не
  собирается, run продолжается (fail-open).
- Воронка реализована строкой `scored -> take(candidateK) -> filter { score >= minScore }
  (если включён) -> take(topK)`; настройки читаются из `KbRagSettingsService.load()`
  при КАЖДОМ вызове, поэтому изменения применяются без перезапуска backend.

## 3. Параметры и настройки

Настройки **глобальные** (не per-base: все базы используют одну эмбеддинг-модель,
распределения score сопоставимы). Хранение — таблица `app_settings` (ключи
`kb.filterEnabled`, `kb.minScore`, `kb.candidateK`, `kb.topK`, `kb.rewriteEnabled`),
переживают перезапуск backend.

| Параметр | Тип | Диапазон | Дефолт | Смысл |
|---|---|---|---|---|
| `filterEnabled` | boolean | - | `false` | включать фильтр релевантности по порогу |
| `minScore` | number | 0..1 | `0.35` | порог cosine: ниже порга чанк отбрасывается (действует только при `filterEnabled=true`) |
| `candidateK` | int | 1..100 | `8` | сколько лучших чанков берётся до порога (верх воронки) |
| `topK` | int | 1..candidateK | `4` | сколько чанков попадает в промпт после фильтра |
| `rewriteEnabled` | boolean | - | `false` | перезапись запроса LLM перед ретривалом (query rewrite) |

- **Дефолты = поведение дня 22** (фильтр выключен, rewrite выключен, topK=4) -> полная
  обратная совместимость: при свежем запуске RAG ведёт себя ровно как до дня 23.
- `GET /api/kb/settings` — текущие настройки (дефолты, перекрытые сохранёнными
  значениями); порченое/нераспознаваемое сохранённое значение = дефолт этого поля
  (load исключений на содержимом хранилища не бросает).
- `PUT /api/kb/settings` — ПОЛНОЕ обновление (все 5 полей в теле; частичных патчей нет).
  Валидация -> 400 с телом `{ "message": "..." }`, сообщения дословно:
  - `minScore должен быть в диапазоне от 0 до 1: <значение>`
  - `candidateK должен быть в диапазоне от 1 до 100: <значение>`
  - `topK должен быть в диапазоне от 1 до candidateK=<candidateK>: <значение>`

  При нарушении валидации ничего не персистится. Кросс-проверка `topK <= candidateK`
  выполняется только в PUT; при чтении воронка сама ограничивает итог числом кандидатов
  (`take(topK)` не выдаст больше, чем есть после порога).
- Изменения применяются к **следующим** ответам без перезапуска backend (свежее `load()`
  на каждом ретривале).

**Где настраивается:**
- REST: `PUT /api/kb/settings` (полное тело); чтение — `GET /api/kb/settings`.
- Фронтенд: хелперы `fetchKbRagSettings` / `updateKbRagSettings` в `frontend/src/api.ts`
  (паттерн существующих kb-хелперов с `raiseKbError`), тип `KbRagSettings` в `types.ts`;
  UI-панель «Настройки RAG» (`KbRagSettingsPanel.tsx`, левая колонка, после «Базы знаний»):
  два свитча «Фильтр релевантности» и «Перезапись запроса (query rewrite)», числовые поля
  `minScore` (0..1, шаг 0.05), `candidateK` (1..100), `topK` (1..candidateK), строка с
  порядком воронки, кнопка «Сохранить» (PUT полным объектом; активна только при наличии
  несохранённых изменений и валидности). Клиентская валидация повторяет диапазоны бэкенда
  (инлайн-ошибки `.kb-field-error`), 400 бэкенда с `{message}` показывается инлайном,
  после успеха — индикатор «Настройки сохранены» (~3 с). Загрузка — GET при монтировании.

## 4. Query rewrite

- **Когда вызывается**: перед ретривалом, ТОЛЬКО при `rewriteEnabled=true` И наличии
  хотя бы одной активной проиндексированной базы (проверка
  `kbRagService.hasActiveIndexed()`). Выключенная настройка или отсутствие активных баз
  = ни одного дополнительного LLM-вызова. Это отдельный вспомогательный LLM-вызов по
  паттерну `AgentImpl.extractFacts` (`streamChat` + `collectList`, без инструментов,
  тот же обёрнутый клиент), видимый в логе как обычные «Запрос в llm»/«Ответ от llm».
- **Промпт** (`REWRITE_REQUEST_PROMPT`, без системного сообщения): промпт состоит из
  двух user-сообщений — вопрос пользователя, затем ДОСЛОВНО:
  «Переформулируй вопрос пользователя для векторного поиска по базе знаний: сохрани
  конкретные термины, названия моделей и числа, убери вежливость и лишние слова. Верни
  ТОЛЬКО поисковый запрос одной строкой, без кавычек и пояснений. Это служебное сообщение
  — не отвечай на него как на часть диалога.» (запрос ставится последним, чтобы модель
  отвечала на него, а не продолжала диалог по вопросу).
- **Санитайзинг ответа** (`sanitizeRewrittenQuery`): trim, снять ОДНУ пару окружающих
  кавычек («…» / "…" / '…'), обрезка до `MAX_REWRITTEN_QUERY_CHARS = 300` символов;
  если после очистки пусто -> null -> фолбэк.
- **Фолбэк**: `finishReason` = `error`/`tool_calls`, пустой ответ, пустой после очистки
  или любой сбой вызова (LLM API 4xx/5xx, таймаут, сеть) -> warn в серверный лог и
  ретривал идёт по ИСХОДному сообщению пользователя; rewrite НИКОГДА не ломает ответ.
  В логе поиска: `rewrittenQuery` — очищенный переписанный запрос (`null` при фолбэке
  и при выключенном rewrite), `rewriteUsed` — использован ли именно он для эмбеддинга
  (false при фолбэке и при выключенном rewrite).
- Эмбеддится переписанный запрос, а в контекст агента уходит исходное сообщение
  пользователя (ответ строится на нём).
- Цена: +1 LLM-вызов на каждый запрос (~1-3 с задержки) -> по умолчанию выключен.

## 5. Лог поискового движка (воронка в панели «Логи»)

В SSE-лог агента (событие `type="log"`, kind **«Ответ поискового движка»**, detail —
pretty JSON) пишется итог воронки после каждого ретривала:

| Поле | Значение |
|---|---|
| `topK`, `candidateK`, `minScore`, `filterEnabled` | настройки на момент вызова |
| `embeddingModel` | модель эмбеддингов запроса |
| `candidateChunks` | всего чанков в активных базах (до воронки) |
| `scored` | сколько чанков оценено косинусом (все загруженные) |
| `candidates` | сколько осталось после `candidateK` |
| `passedFilter` | сколько прошло порог (при `filterEnabled=false` = `candidates`) |
| `usedChunks` | сколько реально вошло в блок (лимит 6000 символов может сократить) |
| `rewrittenQuery` | переписанный запрос (`null`, если rewrite выключен) |
| `rewriteUsed` | использован ли переписанный запрос для эмбеддинга |
| `chunks[]` | финальные чанки воронки (даже не влезшие в блок): `kbName`, `source`, `section`, `score` (cosine, 4 знака), `contentChars`, `content` (полный текст) |

Воронка читается как цепочка `scored -> candidates -> passedFilter -> usedChunks`.
Векторы чанков в лог не попадают (существующее правило). В той же цепочке записываются
«Запрос в БД»/«Ответ БД» (обращения к `KbRepository`: `listActiveIndexed`,
`chunksOfBases`) и «Запрос в эмбеддинги»/«Ответ от эмбеддингов».

## 6. Режимы сравнения

| Режим | `filterEnabled` | `rewriteEnabled` | Что проверяет |
|---|---|---|---|
| A (базовая линия) | `false` | `false` | RAG дня 22 как есть: топ-4 по cosine без отсечения |
| B (фильтр) | `true` | `false` | Отсечение нерелевантных чанков порогом `minScore` |
| C (фильтр + rewrite) | `true` | `true` | Фильтр + улучшенный запрос для ретривала |

В режиме A `topK=4`, `candidateK` не влияет (порога нет); в B/C калиброванный
`minScore` (итог замера задачи 8 — **0.5**, обоснование в разделе 7). Базовые
ориентиры дня 22 (база 16, 10 вопросов): без RAG 0/1/9, fixed1000 4/3/3, structural
10/0/0 (верно/частично/неверно) — RAG уже силён, фильтр должен держать качество и не
терять ответы, а не «лечить» сломанный поиск.

### Калибровка minScore

По score из логов «Ответ поискового движка» (прогон A, 10 вопросов × топ-4 чанка):
все чанки, реально вошедшие в промпт, имеют score **0.5812–0.8795**; мусора среди
использованных чанков нет. Проверка порога оффтоп-запросом («Как приготовить борщ?»):
топ-4 чанка дали score **0.3651–0.3976** — при дефолтном пороге 0.35 этот мусор
**проходит** фильтр (passedFilter=8) и попадает в промпт; при пороге **0.5** он
отсекается полностью (passedFilter=0 → блок базы знаний не собирается, агент отвечает
без RAG). Итог: **minScore = 0.5** — лежит в зазоре между «мусором» (≤0.3976) и
«полезным» (≥0.5812). На всех 10 профильных вопросах при 0.5 passedFilter = 8
(порог ничего полезного не режет, usedChunks = 4 как в режиме A).

### Выводы

1. **Фильтр (A → B): качество не изменилось (9/0/1 → 9/0/1), но появился защитный
   порог.** На профильных вопросах фильтрация — no-op (все кандидаты и так ≥0.58);
   ценность фильтра в том, что оффтопные запросы перестают протаскивать нерелевантные
   чанки в промпт (при 0.35 «борщ» получал 4 чанка руководства по пылесосу, при 0.5 —
   ни одного). Фильтр включать стоит: он не теряет качество и защищает контекст.
2. **Query rewrite (B → C): +1 верный ответ (9/0/1 → 10/0/0).** Rewrite короткого
   шумного вопроса №9 («Какой объём чистой воды заливается в бак станции LEGEE LuLu?»)
   в «объём бака для чистой воды станции LEGEE LuLu» поднял релевантность нужного чанка
   (0.7314 против топа 0.7717 у нерелевантных в A/B — конкурент-чанк сменился), и модель
   извлекла 3,2 л, которую в A/B стабильно «теряла». Цена — +1 LLM-вызов на запрос
   (~1 с на этом прогоне: режим C шёл 3–12 с против 1–4 с в A/B).
3. **Итоговая рекомендация**: рабочий профиль — `filterEnabled=true, minScore=0.5,
   candidateK=8, topK=4, rewriteEnabled=true` (режим C). Для экономии токенов на
   коротких точечных диалогах допустим режим B (rewrite выключен) — на этой базе
   разница только в вопросе 9.
4. Замер честный, но одноразовый: LLM недетерминирован, вопрос 9 в A/B «отзывается»
   между прогонами (в дне 22 structural давал и 9/10, и 10/10) — устойчивость
   результата C на нём стоит перепроверять при смене модели/базы. Настройки после
   замера возвращены в дефолт.

## 8. Ограничения

- **Недетерминизм LLM**: ответы (и сам rewrite) невоспроизводимы побайтово; сравнение —
  один прогон на режим (как в днях 21-22), недетерминизм фиксируется в выводах.
- **Порог откалиброван в задаче 8**: `minScore = 0.35` — дефолт (= поведение дня 22),
  рабочий порог по замеру — **0.5** (зазор «мусор» ≤0.3976 / «полезное» ≥0.5812, см.
  раздел 7). Cosine не является вероятностью релевантности и зависит от модели
  эмбеддингов, языка и размера чанков: при смене модели или базы порог
  перекалибровать по тому же методу (оффтоп-проба + распределение score).
- **Query rewrite = +1 LLM-вызов** на каждый запрос (~1-3 с) и расход токенов; по
  умолчанию выключен. Rewrite помогает только если исходная формулировка «прошумлена»;
  на коротких точных запросах выигрыша может не быть.
- **Глобальные настройки** (не per-base): один порог на все базы; допустимо, пока все
  базы на одной эмбеддинг-модели (распределения score сопоставимы).
- **Порог срабатывает ПОСЛЕ `candidateK`**: нерелевантный чанк, не попавший в топ-`candidateK`
  по score, порог не «спасёт» и не «отрежет» — он и так выбыл; порог режет только внутри
  верхних `candidateK`.
- **Нет отдельного LLM-реранкера** (вне скоупа задания): сортировка — только cosine.
- **Лимит блока 6000 символов** не меняется фильтрацией: даже пропустив много чанков
  через порог, в промпт уйдёт не больше, чем помещается.
